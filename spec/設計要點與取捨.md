# 設計要點與取捨

> 記錄 w-web-task 開發中的設計決策、取捨與「已知不修」事項, 供後續測試與維護遵循 (對應全域 §3.1 真痛/假痛三條件、§2.3 簡潔優先). 本版已納入設計對抗性審查 (review-design) 結論.

## 決策

### D1. 任務採扁平原子模型, 不做巢狀 multi-task
- **決策**: DB 的 task = 一收一回一終態的原子單元. 「多任務」以同頻道多個扁平 task 表達, 不在單一 task 內存多個 subtask 各自 state.
- **理由**: agent (Claude) 注意力有限, 同時維護多 sub-state 易出錯; 扁平模型涵蓋所有多任務場景 (詳 `設計_agent協定.md` §5) 且 DB 極簡.
- **影響**: 不提供 subtask 巢狀 API; 請求端要拆成多個 task 或一個 task + markdown 步驟.

### D2. 對外 agent 面用 HTTP REST, 對內前端用 kpFunExt
- **決策**: agent 輪詢走 HTTP REST (`apis`); 前端即時操作走 kpFunExt (WebSocket RPC) + useDbOrm 直通. 兩者共用同一 procCore 業務函式.
- **理由**: 輪詢無需持久連線, HTTP 對任意 CLI runtime (curl/fetch) 最易呼叫; 前端純 CRUD 表 (channels/channelMembers) 走 ORM change 即時同步, kpFunExt 較佳.
- **同步策略 (重要)**: tableNamesSync 須與 tableNamesExec 對齊 (僅 channels/channelMembers). messages/tasks **不放 sync** — 它們不在 tableNamesExec (寫入須走 kpFunExt 業務函式保 kmx/守衛/身分權威), 若放進 sync, 同步引擎收到其 tag 變更時找不到對應 select binding → client refreshTable 報 error + 洩漏未解 promise. 故 messages/tasks 前端一律以 `$fapi.getMessages/getTasks` **按需拉取** (選頻道/發送後重抓, 存本地渲染), 非 ORM change 推送.
- **開窗輪詢 (2026-07-06 業主要求補強)**: 純按需拉取會使「聊天視窗開啟期間, agent 的回應不會自動出現, 須切頻道才看得到」. 補強: ChatView 掛載期間每 5 秒靜默輪詢 (`pollRefresh`: 重拉 getMessages/getTasks, 資料有變才更新本地與重繪; 原本捲動貼底才自動捲到底, 不打斷使用者往上閱讀; 背景分頁不輪詢). 仍不走 ORM sync, 上述 select binding 限制不變.
- **影響**: 同一業務有兩個傳輸入口, 認證方式不同 (HTTP→getAndVerifyAppUser; kpfun→verifyConn 連線層).
- **2026-10-14 補記 (D17)**: 原載「useDbOrm 直通」→ 資料通道之表操作只開 `select` (同步用), channels / channelMembers 之寫入只經 kpFunExt; 表操作另經 `authorizeExec` 授權閘. 連線層 (verifyConn) 由「只認證」改為「認證 + verifyClientUser」, 與登入檢查同一授權強度.

### D3. 認證委外 SSO, 本套件不存 users/tokens
- **決策**: 沿用 w-web-api/perm 模式, token 由 SSO 核發, 本端 `getUserByToken` 驗證. 開發 `token=sys` 捷徑 (NODE_ENV!==production).
- **理由**: 需求明示「需接入外部驗證例如 sso」; 不重造認證輪子.
- **影響**: 無本地登入流程; 部署需設 `ssoBaseUrl` / `ssoAppToken`; 測試 mock getUserByToken.
- **agent 身分合約 (2026-07-07 業主確認)**: agent 為機器角色, 建議以 SSO **app token** (tokens 表 isApp='y', userId 欄=agent 識別碼) 認證 — SSO 解析回虛擬使用者 (id=token.userId, name/email 為非空占位值, isAdmin='y'), 大量 agent 無須逐一建真人帳號/email. 一般使用者 token 亦可作 agent 用. 兩者皆須通過 `checkUser` (id/email/name/isAdmin 四欄非空) — `getAndVerifyAppUser` 與 client 路徑對稱 (2026-07-07 補齊, 原僅 iseobj 檢查); app token 之占位值天然滿足, 不受影響. 已以真 SSO 鏈路端到端驗證 (SSO 發 app token → 解析 → checkUser → 輪詢/認領/回報全流程 + 無效 token fail-closed).

### D12. 已知結構性效能上限: ORM 全表掃描 × 輪詢熱路徑 × 無封存 (2026-07-07 文件化)
- **現況**: 底層 w-orm-lmdb 之 select() 為「getRange 全表讀入記憶體 → mingo 過濾」, 無索引查詢 — 即使 select({id}) 單筆查找亦掃全表. getRecentMessages/getRecentTasks 為 agent 每輪輪詢必經, 其成本正比於「全系統 messages/tasks 總筆數」而非該頻道筆數; messages/tasks 無封存機制, 筆數單調成長.
- **量級**: 總成本 ≈ agent 數 × 輪詢頻率 × 全庫筆數. 千筆級掃描為毫秒級無感; 十萬筆級單次掃描可達百毫秒級, 多 agent 每 30s 輪詢時開始有感, 且每輪全表 deserialize 有 GC 壓力.
- **取捨**: 單機 + 中小量級 (數萬筆內) 為本套件合約內場景, 現況可用; 屬「擴展上限」非現行 bug.
- **中長期改善方向**: ①w-orm-lmdb 支援以 channelId 為前綴之複合 key 範圍查詢 (成本改正比於該頻道筆數); ②封存機制 (done 任務/舊訊息移冷表, 熱表僅留活躍資料).
- **方向②已實作 (2026-07-07, 業主拍板)**:
  - 規則: 終態 (done/error) 且 timeDone 逾 `archiveAfterDays` (settings.json, 預設 30, <=0 停用) 之任務、timeCreate 逾齡之訊息 → 由 `procCore.archiveSweep` 搬至 `tasksArchive`/`messagesArchive` 冷表; 守衛「任務相關訊息 (kind=task/taskReply) 不早於其任務離開熱表」.
  - 觸發: WWebTask 初始化註冊 timer (啟動後 30s 首掃 + 每小時一次, locking flag 防重入); timer 不放 procCore → unit 測試可獨立建構退出 (SSO ADR-013 之教訓). 搬移「先 upsert 冷表再刪熱表」→ 中斷重跑冪等.
  - 查詢面: REST `GET /api/getArchivedTasks` / `GET /api/getArchivedMessages` + kpFunExt 同名; 後台任務頁「顯示封存」切換 (唯讀, 重試/回應停用). 封存訊息無 UI 時間軸檢視 (時間軸只呈現熱表, 稽核走 API).
  - 附件: 封存訊息之 attachments file id 仍指向 files 表/dbf 實體, getFile 照常可取.
  - **e2e 確定性**: demo 種子時間戳為固定 2026-01-01 (baseline 所需) 必逾封存齡, 故 e2e 一律以 `test/tools/e2e-settings.json` (archiveAfterDays=0; 2026-09-28 自 `test/` 移入 `test/tools/`) 啟動 backend 停用掃描; 封存邏輯由 unit(archiveSweep 5 案)+api(G1) 覆蓋. e2e／api 之 backend 為 harness 自建之隔離測試實例 (port 11108、工作目錄 `test/_tmp/e2e-harness/root`, 與開發環境之 11008 及 `./db` 分離; 行程所有權規則見 `test/tools/e2e-setup.mjs` 檔頭).

### D4. 任務 DB 不存細粒度進度, 只四態
- **決策**: state ∈ {pending, running, done, error}. 進度由 agent session 內部 (TodoWrite) 管理, 不回寫 DB. 無 updateTaskState API (見 D9).
- **理由**: 降低 agent 回寫負擔與注意力佔用 (D1 同源).
- **影響**: 前端看不到「running 30%」; 只看到「執行中」. 可接受.

### D5. respondTask 同時鏡射一筆 taskReply 訊息
- **決策**: 回應任務時 (done 或 error), 除寫 task.result/state 外, 另 post 一筆 message(kind='taskReply') 到頻道, 兩者同一 kmx 操作原子完成; task.resultMessageId 回指該訊息.
- **理由**: 頻道對話時間軸完整 (問→答都在對話流可見), 同時保留結構化任務終態.
- **影響**: 一次回應寫兩張表; 已用 kmx 序列化保證一致.

### D6. 任務生命週期三動詞共用 kmx 鎖 + state 守衛 (並發正確性)
- **決策**: claimTask / respondTask / resetTask 共用 `kmx('task:'+taskId)` 序列化. 鎖內各檢查來源 state:
  - claimTask: `state==='pending'` 否則 reject `errTaskAlreadyClaimed` (防兩 agent 搶同一任務).
  - respondTask: `state==='running'` 否則 reject `errTaskNotRunning` (防重複回應覆寫終態, 防與 resetTask lost-update).
  - resetTask: `state∈{error,running}` 否則 reject `errTaskNotResettable`.
- **理由**: 對應 CLAUDE.md 雙擊防護後端層; claimTask 有守衛則 respondTask/resetTask 必須對稱否則仍有覆寫窗.
- **影響**: 同一任務的並發操作只有一個成功, 其餘收對應 reject (預期行為非錯誤).

### D7. 訊息去重靠伺服器端游標 (channelMembers.lastSeenMessageId), agent 輪詢無狀態
- **決策**: 每個 (channel, member) 在 channelMembers 列存 `lastSeenMessageId` 游標. agent 每輪 /loop 以 getRecentMessages(afterId=游標) 取新訊息, 處理後 ackChannel 推進游標. agent 不在 session 內維護「已讀集合」.
- **理由**: 使用者以 /loop 驅動 (每輪≈重跑 prompt + session 會重啟), session 內記憶體去重必失 → 漏回新訊息或重複回. 任務面已有 state=pending 持久標記, 訊息面需對等的持久游標才對稱.
- **影響**: 多一個游標欄位 + ackChannel API; saveChannel 設 agentId 時確保 agent member 列, ackChannel 對缺列者 upsert (兩者之「先 select 後 insert」以同一 kmx key 包成原子, 並行不重複建列, 見 D16). 訊息查詢 afterId 用 UUIDv7 + getRange 起點高效取「某 id 之後」.
- **游標 key 讀寫對稱 (關鍵)**: 游標一律以「呼叫者 token 身分 userId」為 member key 讀 (getChannelsList) 與寫 (ackChannel), **不以 agentId 為 key**. agentId 僅用於「過濾哪些頻道由此 agent 主責」. 如此即使部署時 channel.agentId 設為友善名稱 (≠ SSO 解析之 user.id), 讀(userId)寫(userId)仍命中同一列, 不會出現「讀寫不同列 → 游標永不前進 → 訊息每輪重讀」. agent 端因此不需知道自己的 user.id — 只要 ME(agentId) 等於主責頻道 channel.agentId 即可過濾出頻道, 游標由 server 依 token 自動對應.
- **自產訊息去重**: agent 同輪以 respondTask/postMessage 產生的訊息 (taskReply / 自己的 text) id 必大於本輪游標, 下輪 getRecentMessages 會讀到; agent 回話前須濾掉 `senderId===自己 && kind!=='text'` (只對他人的 text 回話), 且 ackChannel 的 lastMessageId 取「本輪讀到最新 id 與自己 post 最新 id 之較大者」, 使自產訊息納入游標. 詳 設計_agent協定 §6.

### D8. 身分權威一律取自 token, 不信任呼叫端自帶識別碼
- **決策**: 寫入的 senderId / assigneeId / 稽核 userId 一律 = getUserByToken(token) 解析之 user.id. claimTask 不收 agentId 參數 (assignee 由 token 定). senderType 由呼叫端宣告但僅供 UI 呈現, 非授權依據. getChannels 的 agentId 為**查詢過濾**參數 (過濾 channel.agentId), 非身分宣告.
- **理由**: 防冒名認領/冒名發話; 對齊「senderId=agent 自身識別碼」自證原則; 與全表 userId 稽核欄位慣例一致.
- **影響**: 單一 agent 的 assigneeId 與 taskReply senderId 必一致 (皆 token 身分), 稽核可靠.

### D9. 移除 updateTaskState, respondTask 為唯一終態入口
- **決策**: 不提供 updateTaskState. 終態 (done/error) 一律走 respondTask (一律鏡射 taskReply); error→pending 走 resetTask.
- **理由**: updateTaskState 與 respondTask(error) / resetTask 語意重疊, 且經 updateTaskState 進 error 不鏡射訊息會破壞 D5「問→答都在對話流可見」; 收斂職責更簡潔 (§2.3).
- **影響**: error 錯誤說明一律寫 task.result (人類可讀), errorKey 為選填 i18n key (供統計, 不放自由文字); 前端讀錯誤只看 result.

### D10. 內容渲染與檔案服務之 XSS 防護 (兩個安全不變量)
- **背景**: message.content / task.payload / task.result 允許 markdown (D 設計), 後端刻意以 woItems 直存不過 clearXSS (保留 markdown 原樣, procCore.mjs:19); 前端 ChatView / LayoutContentTasks 以 showdown `makeHtml` → `v-html` 渲染. showdown **不消毒** HTML, 故原始 `<script>` / `<img onerror>` / `javascript:` 連結會穿透 → 儲存型 XSS (任一具發訊權限之 human/agent 可在所有檢視者瀏覽器執行 JS, 竊 userToken).
- **決策 (不變量 1 — 渲染消毒)**: 所有 `renderMd` 一律 `DOMPurify.sanitize(mdConverter.makeHtml(c))` 後才交 `v-html` (ChatView / LayoutContentTasks 兩處). **移除此 sanitize 即 XSS 復活**; E2E-007 為其回歸守衛 (發 `<img onerror>` 訊息, 斷言 onerror 未執行 + DOM 無 onerror 屬性 + 文字保留).
- **決策 (不變量 2 — 檔案服務白名單)**: getFile (WWebTask.mjs) 僅點陣圖白名單類型 (png/jpeg/gif/webp/bmp/avif) 以原 Content-Type + `inline` 呈現; 其餘 (含 `text/html` / `image/svg+xml` 等可挾帶 script 者) 一律 `application/octet-stream` + `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff` → 強制下載不於本站原點 inline 渲染. **理由**: 上傳之 type/name 不可信 (使用者自帶), 若以原 type inline 服務惡意 HTML/SVG 即為同源 XSS. api-files 測試「getFile 非白名單類型 → 強制 attachment + octet-stream + nosniff」為其守衛.
- **非問題 (已查核)**: readFile 之 `path.join(dbfDir, id)` **無路徑穿越風險** — id 須先命中 files 表 (`select({id})`) 才到 path.join, 而 file id 為 `genIDSeq()` 伺服器產生之 UUID (非使用者可控), `../` 之類 id 不存在於 files 表即被擋. files 表查詢即白名單.

### D13. RWD 採 master-detail 堆疊, 斷點 768px (2026-07-06 實作)
- **背景**: v2 UI 重設計 (§10) 將 v1 之響應式 `WDrawer` 換成固定 flex 版面 (rail 64px + 頻道樹 282px + 內容區), 窄屏時 rail + 樹即占滿寬度, 內容區被擠出畫面右緣 → RWD 失效 (390px 實測確認).
- **決策**: 以 `$store.state.isNarrow` (由 `Layout.vue` 之 `resize` 監聽維護, 斷點 `window.innerWidth < 768`) 驅動版面切換:
  - **頻道區**: 窄屏改 master-detail —— 未選頻道→頻道樹全寬; 選了頻道→聊天區全寬 + 標題列左側「返回」鈕 (`onClickBack` 清空 currentChannelId). 標題列同時以 media query 隱藏次要項 (breadcrumb / 任務 pills / agent chip) 避免溢出.
  - **後台**: 窄屏子選單改頂部橫向 tab (Channels/Members/Tasks), 資料表於下方全寬.
  - **統計 / 成員視窗**: 原生已響應 (`flex-wrap` / `WDialog` 之 `autoFullscreenWhenNarrow`), 不另處理.
- **理由**: master-detail 為聊天類應用之行動端標準模式 (先看清單→進對話→返回); 相較「縮小樹寬」可保留內容區完整可用寬度.
- **關鍵影響 (勿破壞)**: **斷點以下之版面切換一律經 `isNarrow`, 桌面 (≥768px) 版面必須與改動前逐像素相同** —— e2e 於 `viewport 1440×900` 執行 (`test/tools/e2e-setup.mjs` 之 `openApp`; 原載行號錨 `test/e2e-setup.mjs:229` 已隨重構位移, 2026-09-28 改為符號錨), `isNarrow=false`, 故所有既有 pixel baseline 不受影響. 日後調整 RWD 時, 若動到 ≥768px 之版面即會觸發 baseline mismatch, 屬預期.

### D14. 成員類型在地化採 cell-render「顯示層映射」, 底層仍存原值
- **背景**: 成員資料表之 `memberType` 欄原以原始 enum (`agent` / `human`) 顯示. 其在地化不可經「轉換 `opt.rows` 資料」達成 —— `doSaveMembers` 直接讀 `opt.rows` 送 `saveChannelMember` (`LayoutContentMembers.vue`), 轉換底層值會把在地化字串寫進 DB (資料污染).
- **決策**: 以 WAggridVue 之 `cell-render` slot 僅轉**顯示**文字 (`$s.getMemberTypeText`), 底層 `row.memberType` 維持原值 `agent`/`human` 供儲存. 此與 `LayoutContentTasks` 之 `state` 欄以 `cell-render` 上色 + 在地化為**同一慣例**.
- **取捨 (明知且接受)**: ag-grid 之欄位文字過濾器比對的是**底層原值**而非渲染後文字, 故於成員表輸入「人類」過濾不會命中 (需輸入 `human`). 成員表為每頻道數列之小表, 實務上不會用打字過濾 → **後果不具體, 不修**. 若日後出現大量成員之頻道再評估.

### D15. 注入函數失敗不外洩上游原文 (W 契約)、權杖遮罩 (M 契約)、getUserIdByToken fail-closed (2026-09-25)
- **背景**: 部署方回報 (2026-09-24, 經 w-web-sso 權杖外洩修正方案 v2 全盤盤點, 對應 sso ADR-068 同日新增): 部署方常把 w-web-sso 對外 helper 直接注入為 `getUserByToken`, 舊版 helper 失敗時以「已代入介接權杖 (app token) 與使用者權杖之完整網址」reject; 本套件未攔截, 原文經四個通道外流 —— C1 HTTP 回應 (`/api/getUserByToken`、`getChannels` 等 app 路由、`/api/getFile` 之 404 JSON)、C2 srLog (`runApi` / getFile 之 `err` 欄)、C3 後端 console、C4 w-converhp 之 console 與 error 事件. `verifyClientUser` / `verifyAppUser` 之拋錯走同一路徑. 外洩之 app token 於 sso 端等同全權系統管理者 (sso ADR-005), 後果見 sso ADR-068. 同案另查出: 原 `maskTok` (前 4 碼 + `***`) 不處理陣列 (Hapi 對重複 `?token=` 給陣列 → 原樣印出)、`/api/getUserByToken` 無效分支整包印 `req.query`、`srv.mjs` 印 `err.message` (請求例外之 message 可含已代入權杖之網址)、`getUserIdByToken` 查無時回 `''` 並繼續執行函數 (fail-open). 修正前以合成權杖實機探測, 四通道皆重現.
- **決策 1 (W 契約, `server/wrapInjected.mjs`)**: `WWebTask` 於 srLog 初始化後, 以 `wrapInjected` 包裝版**取代三個注入參數本身** —— 其後所有呼叫點 (含日後新增者) 結構上只可能用到包裝版. 上游同步拋錯或 reject 時視同否定結果: `getUserByToken` 回 `null` (查無)、`verifyClientUser` / `verifyAppUser` 回 `false` (無權限), 走各呼叫點既有分支, 對外只回自家 key (`errUserNotFound` / `errUserNoPermission` / `errUserIdMissing`). 失敗記 `srLog.warn({ event: 'inject-<函數名>-fail', ...describeUpstream(err) })`: reject 值 (或 `Error.message`) 屬 sso K 契約 14 個 key 者記 `{ upstream: key }`, 否則只記 `{ upstreamType, upstreamName }` (型別與名稱形狀之 `Error.name`), **絕不記原文**. 對外刻意不區分「SSO 不可達」與「權杖無效」(防列舉, 與 perm helper 一致), 區分只放在 log 之 `upstream`.
- **決策 2 (M 契約, `server/maskLog.mjs`)**: 印權杖一律經 `maskTok` / `maskQuery` / `maskUrl` (取代原 `WWebTask.mjs` 內之 `maskTok`). `maskTok`: `undefined`/`null`/`''` → `''`; 陣列逐元素; 字串取 `k=min(4, floor(n/8))`, `k=0` → `(len=n)`, 否則 `前k...後k(len=n)` 且露出之控制字元換成 `?`; 其他型別 → `(typeof)`. 與 sso `maskToken`、perm / api `maskTok` 同一組測資; 36 字元 session token 之輸出與 sso 現行格式相同. `maskQuery` 淺拷貝並遮罩鍵名小寫為 `token` 者 (非物件依 M 契約遮罩); `maskUrl` 語意同 sso `src/maskUrl.mjs`: http(s) 只留 origin + pathname, 非 http(s) (如 `data:`, 其 pathname 即內容) 只回 protocol, 無法解析回 `(invalid-url)`.
- **決策 3 (查無語意對齊, 方案 S7–S9)**: `getTokenUser` 補 `isestr(token)` 守門與 `iseobj` 檢查 → 查無一律 `errUserNotFound` (遮罩印 token), 成為 token → 使用者之唯一出口: `p.checkToken` (連線閘) 與 `getAndVerifyAppUser` 皆改經 `getTokenUser` (原各手寫一份, 同一規則收斂一處). `getUserIdByToken` 改 **fail-closed** (對齊 perm): token 非字串或查無 userId → `srLog.error({ event: 'getUserIdByToken', err: 'errUserIdMissing' })` 並 reject `errUserIdMissing`.
- **決策 4 (參考部署 `srv.mjs` 與前端)**: SSO 請求例外只印 `err.name`、`cause.code` 與 HTTP 狀態碼, 不印 `err.message`. 新增兩個測試權杖 (與 `sys` 同樣以 `NODE_ENV !== 'production'` 守門): `{token-for-reject}` (getUserByToken 以舊版 helper 形狀之字串 reject, 內夾合成秘密) 與 `{token-for-verify-throw}` (解析為合成使用者 `id-for-verify-throw`, 其 verifyClientUser / verifyAppUser 拋出夾合成秘密之 Error), 供 `test/api-tokenLeak` 驗證. `public/index.html` 加 `<meta name="referrer" content="strict-origin">`: 以 `?token=` 開站時, 同源請求之 Referer 只帶 origin (縱深防禦; 本套件 verifyConn 本不記 referer, 反向代理之 Referer 欄亦不再含權杖).
- **行為變更 (如實記載)**:
  - `getUserIdByToken`: 修正前 token 非字串或查無 userId 時回 `''`, 資料通道 execute **照常執行函數** (函數收到 `userId=''`); 修正後 reject, 函數不執行, 前端收到 w-serv-webdata 之 `execFun func[...] has an error: undefined` (該套件以 `err.message` 組訊息, 字串 reject 無 message; 屬方案 N8 套件層, 本案不處理). 正常前端流程之 Authorization 與 `__sysToken__` 取自同一 `getToken`, 不受影響 (e2e 全綠為證).
    - 2026-10-14 補記 (原載「前端收到 `execFun func[...] has an error: undefined`」→ 改為): 上句為 w-serv-webdata 1.1.6 時之行為; 1.1.12 起 execFun 以拒絕值原樣為回應之 msg (`node_modules/w-serv-webdata/src/WServWebdataServerExec.mjs:278-286`), 前端改收自家 key `errUserIdMissing` (`server/procLang.mjs` 有此鍵, `$tErr` 可譯出), 函數仍不執行. `test/api-tokenLeak.test.mjs` E6 / S9 已補斷言此 key.
  - 查無使用者之 key: `/api/getUserByToken` (client 路徑) 與連線閘由 `errUserIdMissing` 改為 `errUserNotFound` (與 app 路徑一致); 使用者存在但缺 id/email/name/isAdmin 仍回 `checkUser` 之對應 key.
  - 注入函數拋錯或 reject: 修正前原文上拋 (回應 `msg` 即上游字串或 `Error.message`); 修正後依呼叫點回 `errUserNotFound` / `errUserNoPermission` / `errUserIdMissing`.
- **log 筆數 (同一次上游失敗; 包裝處 warn 為因、呼叫點 error 為果)**: HTTP 路由 (`/api/getUserByToken` 與各 app 路由) 2 筆 (`inject-<fn>-fail` + `api/<route>`); `/api/getFile` 2 筆 (+ `api/getFile`); 資料通道 verifyConn 1 筆 (果由 w-converhp 回 `permission denied`, 不寫 srLog); execute 之 `__sysToken__` 2 筆 (+ `getUserIdByToken`; 另有已通過之 `verifyConn` info). 查無 (非上游失敗) 無 warn, 只有呼叫點 error. 以上由 `test/api-tokenLeak` 逐筆斷言.
- **盤點指令 (可重跑; 2026-09-29 起規則帳本併記於 `CLAUDE_rulebook.md`「權杖外洩防護」, 本節保留為決策當時之站點全集; 原載「本 repo 無 `CLAUDE_rulebook.md`, 規則與站點全集記於此」)**:
  - 規則一「注入函數只經 wrapInjected」: `git grep -nE "\b(getUserByToken|verifyClientUser|verifyAppUser)\(" -- server/WWebTask.mjs` → 站點全集 (2026-09-25): 參數取代處 (唯一傳入原始函數處) 之後之 `getTokenUser`、`getAndVerifyClientUser`、`getAndVerifyAppUser`、`getUserIdByToken` 四處, 皆用包裝版; 取代處之前只有 `isfun` 檢查. 判準: 呼叫點皆位於參數取代之後.
  - 規則二「印權杖只經 maskLog」: `git grep -nE "console\.(log|error|warn|info)\(.*(token|query|authorization|headers|referer|payload)" -- server srv.mjs` → 權杖值參數之站點全集: `getTokenUser` 之 token、`parsePayload` 之無效本體、`/api/getUserByToken` 無效分支之 `req.query` 與 token (2 處)、verifyConn 之 authorization、`getUserIdByToken` 之 token —— 皆經 `maskTok` / `maskQuery`; 其餘命中行為固定字串 (如 `can not find the user from token`); `srv.mjs` 無命中 (其 SSO 例外行只印 err 名稱、代碼與狀態碼). 判準: 權杖值參數 0 筆未遮罩.   - 規則三「srLog 不記權杖」: `git grep -nE "srLog\.(info|warn|error)\(" -- server` → 無 token / authorization / query / headers / referer 欄; `err` 欄只為自家 key 或 `describeUpstream` 之結果.
  - 同步點: `server/wrapInjected.mjs` 之 `keysUpstream` 須與 sso K 契約 (sso README 之 helper reject 對照表) 一致; sso 增刪 helper key 時同步修改, 並同步 `test/unit-wrapInjected` 之 `KEYS_K`.

### D16. 按鈕雙擊防護補齊——按鈕鎖至請求結束、送出流程狀態、後端依操作者占位 (2026-09-29)

- **決策**:
  1. **前端 (元件層)**: 有副作用之 WButtonChip / WButtonCircle 一律 `:promiseUnlock="true"` (新增: 頻道 / 成員刪除鈕); handler 為 method 名, 把 `msg.pm` 交給送出函式 (`vo.doX({ pm: msg.pm })`), **不於 handler 解鎖**; 鎖於全頁 loading 關閉 (`$ui.updateLoading(false)`, 即請求結束) 時釋放 —— 請求期間滑鼠與鍵盤皆擋, 結果訊息框出現時按鈕已恢復; 有確認框者 (頻道 / 成員刪除、任務重試、登出) 於開確認框前以 runSubmit 傳入之 `unlockBtn` 釋放按鈕鎖 (確認框背後之按鈕不顯示載入圖示), 重入仍由流程狀態擋.
  2. **前端 (送出流程狀態)**: `src/plugins/submitGuard.mjs` (複製自 w-web-sso) 與 `$ui.runSubmit(key, fn, opt)`: 同 key 之流程 (自觸發至結果訊息框關閉) 進行中再觸發即略過, 按鈕、鍵盤 Enter、輸入框 Enter 同一狀態; 被略過之觸發立即釋放其按鈕鎖. key: `postMessage` (發送鈕與輸入框 Enter 共用, 取代 `sending` 旗標)、`saveChannels`、`deleteChannels`、`saveChannelMembers`、`deleteChannelMembers` (後台與頻道聊天頁之成員視窗共用同一元件與 key)、`resetTask`、`respondTask`、`logout` (確認後轉址 / 重新載入時以 `opt.hold` 保持至頁面離開).
  3. **前端 (單例訊息框)**: `CheckYes` / `CheckYesNo` 之 `show()` 開頭若 `vo.pm` 已存在, 先 settle 前一個等待者 —— `CheckYes` 視同已按確定 (`resolve()`)、`CheckYesNo` 視同選否 (`reject('close')`); 對已結束者無作用 (與 w-web-sso 同一修正). 因 runSubmit 之占位涵蓋至結果訊息框關閉, 訊息框開啟中若又有另一流程開框 (鍵盤 Enter 可觸發背後另一按鈕), 未 settle 之前一流程將永久等待、其 key 永不釋放, 該操作再也無法觸發. 呼叫端相容: `showCheckYesNo` 4 處皆接 `.catch(() => {})`, `showCheckYes` 13 處皆 `await` 後收尾.
  4. **後端 (依操作者占位)**: `server/lockSave.mjs` (複製自 w-web-sso) 之 `lockSave(op, operatorId, fn, opt)` 以 cacheSt 原子占位: 同一操作者之同一操作 (或同一列) 處理中再送出 → reject, **不排隊** (排隊後再寫一次即覆寫); 不同操作者互不影響. 站點與 key:
     - `saveChannel:{userId}:{id | name}`、`saveChannelMember:{userId}:{id | channelId:memberId}` → `saveInProgress` (只擋同一列之連發, 同批其他列不受影響);
     - `deleteChannel:{userId}:{id}`、`deleteChannelMember:{userId}:{id}` → `deleteInProgress` (`opt.errKey`);
     - `postMessage:{userId}:{channelId}` (包在既有 kmx 外層) → `sendInProgress`; 依序再送同樣內容為使用者之新訊息, 不擋.
     - 三 key 之 eng / cht 加於 `server/procLang.mjs`; 錯誤 key 之 log 沿 `wrapErrLog` / `runApi`.
  5. **後端 (「確保成員列」原子化)** (2026-10-23 已由 D18 之表鎖取代: 主責 agent 成員列於清單 / 單筆存檔之表鎖內補建, `ackChannel` 缺列路徑取表鎖後重查; 以下為原作法之記載): `saveChannel` 之主責 agent 成員列與 `ackChannel` 之游標列, 其 select 後 insert 以 `kmx('channelMember:'+channelId+':'+memberId)` 包成原子. 兩路徑寫同一 (channelId, memberId) 列, 故**共用同一 key** (呼叫者即主責 agent 時兩路徑互斥; 各用各的 key 仍會重複建列, 見背景之重跑). `ackChannel` 為 agent 輪詢之游標推進 (非按鈕), 只序列化、不拒絕.
  6. **建立位置**: `cacheSt` 內含 TTL 偵測 timer (未 unref 之 setInterval), 故 `cst` / `lockSave` 於 `server/WWebTask.mjs` (kmx 旁) 建立並經 deps 注入 procCore, 不在 procCore 內建立 —— procCore 保持無 timer, unit 測試可獨立建構退出 (同 D12 封存 timer 之安排; w-web-sso 建於 procCore 內, 本專案因此偏離).

### D17. 配合 w-serv-orm 移除使用者檢查設定; 資料通道只開 select 並套用 verifyClientUser (2026-10-14)
- **狀態**: 採行 (主控裁決 2026-10-14: A1、B1、C1; 審計紀錄見 run01 審計回應).
- **背景 (皆以已安裝版本之原始碼與 2026-10-14 實跑為證)**:

### D18. 多人同時編輯之寫入契約——清單級 API、基準比對、表鎖、補償還原、草稿保護 (2026-10-23)
- **狀態**: 採行 (使用者 2026-10-22 裁示原則 10; 規格 `C:\opensrcOper\dspec\多人同時編輯之寫入契約.md` 規格 1; 主控 2026-10-22 對本套件盤點之處置 Q1～Q8, 見 `sgud/rule/rulebook_concurrency.md` 與其分冊). 取代 D16「後端 (『確保成員列』原子化)」之共用 kmx key 作法 (改為表鎖, 見下 3、4); D16 之 lockSave 占位與前端 runSubmit 不變 (清單級 API 之 key: `saveChannels:{userId}`、`deleteChannels:{userId}`、`saveChannelMembers:{userId}:{channelId}`、`deleteChannelMembers:{userId}:{channelId}`).
- **背景 (inv01 盤點實證, 修前探測皆為紅)**: 頻道頁與成員頁原以前端逐列迴圈呼叫單筆 API, 造成 (E4) 中途失敗之部分寫入與重試重複建列; (E3) 成員存檔整列回寫, 把 agent 已讀游標寫回舊值; (E2) `archiveSweep` 以掃描初期之舊列搬冷表, 掃描期間被 `resetTask` 重置之任務被刪而消失; (E7) 頻道頁收到資料通道推播即重建整張表, 草稿靜默消失; (O1) 修改已被刪之列使其復活; (O2) 刪除不存在之列仍回成功; (O3) `ackChannel` 與刪成員競態產生殘缺列; (O4) `(channelId, memberId)` 可重複; (O5) 後端不驗頻道名稱; (O6) 存檔採用客戶端之 userId / timeCreate / isActive; (O7) 刪頻道不清引用、可對已刪頻道發訊; (O8) `respondTask` 兩段寫入第二段失敗後重試產生重複 taskReply.
- **決策**:
  1. **每表一份寫入契約** (`src/schema/contracts/*.mjs`, 前後端 import 同一檔; 欄位明列不以排除法推得, 全欄 = pk ∪ fields ∪ serverOnly 有單元測試守): `channels` fields = name / description / agentId / levels / ownerId, 餘為伺服器專有; `channelMembers` 為**契約工廠** `getMembersContract(channelId)` (scope = 該頻道; fields = channelId / memberId / memberType / role, `lastSeenMessageId` 為伺服器專有). 無雙方欄位、無 `orderKey` (order 不由後台編輯). 其餘 5 表無整表存檔, 宣告全欄伺服器專有 (`fields: []`, 不交 `checkContract`).
  2. **清單級 API** (取代前端逐列迴圈; kpFunExt): `saveChannels(rows, { baseline })`、`deleteChannels(ids, { baseline })`、`saveChannelMembers(channelId, rows, { baseline })`、`deleteChannelMembers(channelId, ids, { baseline })`. `opt` 只取 `baseline` 一鍵 (其餘客戶端夾帶之鍵一律忽略; procOrm 之 opt 規則不涉本套件). 基準由前端對**畫面所見之同一份列**以共用 `buildBaseline` 自算 (頻道為整表、成員為該頻道有效成員); 後端於表鎖內新鮮讀取並以 `guardWrite` 比對, 不符整次拒收零寫入. 回傳 `{ inserted, modified, deleted, unchanged, rows }`, **`rows` 為寫入後表鎖內之新鮮讀取, 前端以之取新基準與畫面** (不以送出值當新基準: 寫入時 clearXSS 可能改寫字串). 刪除之基準只含被選取列 (他列被改不擋; 先刪先贏); 刪除集合 = 基準內 − 送出 (不得為庫內全部 − 送出); 帶基準時未改動之列 (摘要相符) 不寫入、不蓋稽核欄; 不帶基準 (外部呼叫) 時有 id 者只改不增 (列不存在 → `rowNotFound`, 整次零寫入)、無 id 者新增、無刪除集合、容許部分欄位. 拒收鍵一律以 `getRejectKey` 取得並轉本套件語系鍵: `baselineMismatch → saveStale`、`rowNotFound → errRowNotFound`、`baselineFormat → errBaselineFormat` (皆為「畫面資料過期」, 提示重新載入); `rowsInvalid → errRowsInvalid` (伺服端資料異常, 記 log, 重新載入無解).
  3. **鎖**: 每表一鍵、全程共用 WServOrm 實例之 `withTabLocks` / `guardWrite`; 取鎖序恆為 lockSave (不排隊之雙擊占位) → 表鎖 (依表名碼元序: `channelMembers` < `channels`; 一律一次宣告兩表) → 實體鎖 (`task:<id>`、`channelMember:<c>:<m>`). 所有 channels / channelMembers 寫入者取表鎖: 清單 API 與單筆 API、`ackChannel` 缺列路徑、`postMessage` (於 `channels` 表鎖內重查頻道存在再寫入, 不被刪頻道插入); 同一呼叫鏈不巢狀取同表. 清單 API 在表鎖內對「刪除成員」「成員改名 (memberId)」再取 `channelMember:<c>:<m>` 實體鎖 (表鎖 → 實體鎖, 與 ack 更新路徑同一把): 刪除前像於實體鎖內重讀 (ack 於其前推進之游標納入前像, 補償不撤銷已成功之 ack), 改名於鎖內寫入 (進行中之 ack 先完成, 不把某成員之游標寫進已換人之列).

### D19. 刪頻道時該頻道之訊息與任務移入封存表; 儲存格編輯器開啟中視同草稿 (2026-10-23)
- **狀態**: 採行 (使用者 2026-10-23 裁示 D18 待裁示 Q2:「移入封存表」; 另 task-verify01 N1 / 排程項第 115 項. 任務 task-run02). 補完 D18 第 7 點; 不改狀態機規則、不改 D18 之清單級 API / 游標 / 封存競態 / 單筆收緊.
- **背景**: D18 之刪頻道只連帶刪成員列, 該頻道之訊息與任務留在熱表成為孤兒 (仍計入 `getStats`; 原則 6 要求引用連帶清理, 但直接刪除屬刪除使用者資料, 須使用者決定 → 裁示移入既有封存表). 另 task-verify01 N1: 後台頻道頁之儲存格編輯器已開啟、已輸入未按 Enter 時收到他人推播, 因輸入尚未進列資料而被當作「無草稿」整張重建, 編輯器關閉、輸入靜默丟失 (與 E7 同類症狀).
- **決策**:
  1. **訊息與任務整列移入既有封存表** (`messagesArchive` / `tasksArchive`; D12 之冷表, schema 與熱表相同, 搬入之列與搬移前逐欄相同, 以 `getArchivedTasks(channelId)` / `getArchivedMessages(channelId)` 讀取): 凡 `channelId` 屬該頻道之列一律搬 (不依 `isActive` 過濾, 不留隱藏孤兒). **不增 schema 欄標示「來源頻道已刪除」**: 封存表 schema 依 D12 與熱表同構 (共用 `funNew` 與契約), 增欄須動兩份 schema、契約與既有資料; 且已刪除可由「封存列之 `channelId` 不在 `channels` 表」得知 (頻道 id 為 UUID, 不重用), 資訊不缺.
  2. **同一次操作、同一組鎖、同一補償範圍**: 搬移與成員連帶刪除、頻道列刪除同在 `channels` + `channelMembers` 表鎖內 (清單刪除、清單存檔之刪除集合、單筆刪除三入口共用 `buildChannelDeleteOps`), 寫入單元依序為: 任務 (逐筆) → 訊息 (整批) → 成員列 → 頻道列. 鎖序依既有規則: 表鎖 → `task:<id>` 實體鎖 —— 每個任務於其 `task:<id>` 鎖內重讀再「先 upsert 封存表、再刪熱表」 (與 `claimTask` / `respondTask` / `resetTask` / `archiveSweep` 互斥; 搬走後它們於鎖內重讀得 `errTaskNotFound`, 不回寫已離開熱表之列; 列已被封存掃描先搬走者略過). 訊息於全部任務搬完**之後**才讀取 (任務搬走後不再有 `taskReply` 新增; 發訊被 `channels` 表鎖擋在刪除之外), 故讀到之集合即最終集合, 含等鎖期間完成之回應鏡射. 訊息之搬移與補償於 `msgarch:<channelId>` 鎖內 (見第 6 點).
  3. **全有或全無**: 比照 D18 補償 (`runOps`): 任一寫入失敗 (含 ORM 回 `ok:0` 含批次中部分列 `ok:0`、熱表刪除未命中) 反向補償 —— 熱表補回前像、刪**本次新增之**封存複本 (搬移前封存表已有之同 id 列不刪: 中斷後重試遇「冷熱並存」之殘留者, 補償後仍冷熱並存, 不遺失; 該殘留列內容已被熱表前像覆寫, 為中斷之中間態) —— 全部補償成功回 `saveRolledBack` (封存表原無之列, 庫內與刪除前完全相同), 補償亦失敗回 `saveWriteFail` (記 log). **補償與搬移對稱持鎖**: 任務補償於 `task:<id>` 鎖內、訊息補償於 `msgarch:<channelId>` 鎖內 (外審 sol#1 / #2). **頻道列最後刪**: 本次請求涉及之**全部頻道**之搬移與成員列刪除完成後才刪各頻道列; 中途中斷 (行程崩潰等, 補償來不及) 時全部頻道仍在, **原請求重送即補完** (搬移冪等, 封存表不重複), 不會留下「頻道已刪而訊息 / 任務仍在熱表」之孤兒, 多頻道亦同 (外審 sol#5). 成功後記 `channelArchived` log (頻道 id 與實際搬移之任務 / 訊息筆數; 訊息筆數為鎖內讀到者, 掃描已先搬走者不計, 外審 sol#6).
  4. **進行中任務 (非 done / error) 一併搬移, 維持原狀態 (快照), 不拒絕刪除** (依原則 3「收嚴＋提示」與原則〇之一③「不刪使用者資料」判定): ①拒絕刪除會使頻道可能永遠無法刪除 —— 後台任務頁僅能對 `running` 任務人工回應 / 重置, `pending` 任務無 UI 可結案, agent 失聯時該頻道即無法刪除; ②搬入封存表不刪任何資料; ③「收嚴」落在搬走後不可再認領 / 回應 / 重置 (回 `errTaskNotFound`), 其後不可能出現於熱表流程; ④「提示」落在刪除確認框 (`deleteChannelConfirm`, eng + cht) 明示「訊息與任務 (含進行中者) 將一併移入封存, 且不可再認領或回應」. 不改寫任務狀態 (改成 `error` 等同新增一條熱表以外之轉移, 屬狀態機規則, 本輪不改).
  5. **統計**: 熱表不再含已刪頻道之訊息 / 任務, `getStats` 自然不計 (task-verify01 N4 之孤兒不再發生); 封存表不計入統計 (D12 既有).

### D20. 呼叫者身分驗證與存取矩陣——執行身分完整驗證、函數層級之角色與成員檢查、系統函數收緊 (2026-10-25)
- **狀態**: 採行 (使用者 2026-10-23 裁示 C2 採②「套件自行強制: 管理類限系統管理者、訊息與任務限頻道成員」、C3「執行身分須與連線閘同等完整」; 2026-10-24 token 權責 (應用系統 token 兩種用途); 主控排程第 125、128 項. 規格: `C:\opensrcOper\dspec\使用者身分驗證原則.md` 二.1～二.8、二之一, `w-web呼叫者身分驗證.md` C2 / C2b / C3, `w-web存取管控表.md`. 任務 task-run01). 取代 L1「頻道成員權限弱 enforcement」與 L5「UI 內無額外權限判斷」之後端部分 (下方已加補記).
- **背景 (修前以 `test/api-callerMatrix.test.mjs` 初版 70 案對 HEAD 伺服端實測: 65 案紅 / 5 案綠, 矩陣格級 102 格不符)**: ①**C3**: `getUserIdByToken` 只取 `getUserByToken` 的 id, 資料通道請求之標頭 token (連線閘) 與本體 `__sysToken__` (執行身分) 可為不同 token——標頭為放行者、本體為被 `verifyClientUser` 拒絕者或欄位不齊者時, 函數照常以被拒者之身分執行 (實測 `getWebInfor` 以 `{token-for-nonadmin}` 為本體成功). ②**C2**: 頻道管理類函數 (`saveChannel(s)` / `deleteChannel(s)` / 成員五個) 無角色檢查, 一般使用者可建立、刪除頻道與成員, 全靠部署方 `verifyClientUser` 把關. ③**C2b**: 訊息與任務之讀寫、已讀游標、成員名冊無成員檢查——任一通過連線閘者可讀寫任一頻道; **`ackChannel` 之缺列路徑會替非成員建立成員列 (自我加入任何頻道)**; `getChannelsList`、`getStats`、資料通道 `channels.select` / `channelMembers.select` 回整表; 檔案以 id 取用無身分關卡. ④系統函數: `[sys:polling]` 無 token (已發布前端元件之輪詢不帶 token) 時以無身分放行.
- **決策**:
  1. **執行身分完整驗證 (C3, 規格二.2)**: 新增 `authToken(token, from)` 為瀏覽使用者 token 完整驗證之**單一擁有者** —— `getTokenUser` (解析、欄位齊備; 本套件無自有使用者表, 「使用者存在且啟用」由部署方 `getUserByToken` 查無即回 null 保證) → 已包裝之 `verifyClientUser(淺拷貝, from)`. 連線閘 `p.checkToken`、登入檢查 `getAndVerifyClientUser`、執行身分 `getUserIdByToken` 三者共用, 不另寫第二份. `getUserIdByToken` 之 `from` 固定為 `'main'` (資料通道函數只由 `/api/main` 之 execute 觸發, 與連線閘之 `apiType` `'main'` 為同一入口, 部署方依 `from` 之政策因而一致). 認證失敗 (token 非字串 / 查無 / 欄位不齊) 與授權不通過皆 reject `errUserIdMissing` (函數不執行、不回顯原因); 原因只入 srLog: 認證失敗 `err:'errUserIdMissing'` (同修前), 授權不通過 `err:'errUserNoPermission'`; console 只印 `maskTok`. 通過者以 `access.remember(user, seq)` 登錄角色 (`seq` 為驗證開始時取之單調序號) (見 3). 交給鉤子的是淺拷貝: 鉤子改寫傳入物件不影響其後之角色判斷.
  2. **角色來源 (規格二.4; 擇一並寫明理由)**: 系統管理者 ＝ token 經部署方 `getUserByToken` 所回使用者之 `isAdmin` 嚴格等於 `'y'` (自有屬性; `'Y'`、`true`、`'y '`、繼承屬性等一律視為一般使用者), 判準單一擁有者 `access.isAdminUser`. **理由**: D3 認證委外 SSO, 本套件無自有使用者表, 無從以「本系統使用者表」為權威 (同 w-web-api; w-web-perm 因有自身 users 表而以該表為權威). **應用系統 token**: 使用者用途於 sso 反查回所綁使用者之實際資料, `isAdmin` 即所綁使用者者, 與使用者 token 同; 系統服務用途反查回 `id='app:<金鑰主鍵>'`、`isAdmin='y'`, 即系統管理者等級 (規格二之一.3、5b: 是否簽發由專案方負責). 故本套件**不讀 `isApp`**, 一律以 `isAdmin` 判等級 (部署方 `getUserByToken` 契約不新增必填欄位, 不影響既有部署). **頻道管理者角色: 本套件不設**: `channelMembers.role` 為後台可編之自由文字欄 (`owner` / `member`)、`channels.ownerId` 亦為後台可編欄, 皆無強制語意, 不得作為授權依據; 管理類一律限系統管理者.
  3. **入口函數表 `createGuardedFuncs` (`server/access.mjs`) 為授權之單一套用點**: 資料通道 `kpFunExt` 24 個與 HTTP REST 之 15 條路由 (含 `getFile`; 第 16 條為登入檢查 `/api/getUserByToken`, 直接走 `authToken` 並只回投影後之使用者, 屬認證特例) 皆經同一張表取得函數 (`gf.<名>(caller, ...args)`), procCore 不做授權、WWebTask 內不再有 `pc.<業務函數>(` 之直接呼叫 (盤點指令見 `rulebook_security.md` R-AUTHZ-02). 資料通道之函數只收 `userId` (w-serv-webdata 將 `getUserIdByToken` 回傳值交給函數), 故角色於 `getUserIdByToken` 完整驗證當下登錄於記憶體 `kpCaller` (userId → { isAdmin, 時間 }), 函數呼叫前以 `access.callerOf(userId)` 查回; 無登錄、逾期 (60 秒) 或 userId 非字串一律拒絕 (`errUserIdMissing`, fail-closed). 登錄只由 `getUserIdByToken` 通過後寫入 (前端與外部無法寫入); 每個函數呼叫前皆先經它重新驗證並刷新登錄, 登錄只供其後毫秒級之同一呼叫使用; 角色變更時以**最近開始之驗證**為準 (同一 userId 並行驗證之完成順序可能顛倒: 晚完成但較早開始者不得覆蓋較晚開始者, `unit-access` A2c; 外審 opus#7 / sol#7). HTTP 路由直接以 `getAndVerifyAppUser` 回傳之使用者物件取得角色 (`callerOfUser`), 不經登錄.
  4. **規則 (分類 → 呼叫者 → 拒絕鍵)**: `admin` 管理類 (`saveChannels` / `deleteChannels` / `saveChannel` / `deleteChannel` / `saveChannelMembers` / `deleteChannelMembers` / `saveChannelMember` / `deleteChannelMember`) → 限系統管理者, `errUserNotAdmin`; `channel` 頻道內容 (`getChannelMembers` / `getMessages` / `postMessage` / `getTasks` / `getArchivedTasks` / `getArchivedMessages` / `ackChannel`) → 系統管理者或該頻道成員, `errChannelNotMember`; `task` (`getTask` / `claimTask` / `respondTask` / `resetTask`) → 系統管理者或任務所屬頻道成員, 一般使用者查無與非成員**同回 `errTaskNotFound`** (不洩漏任務存在與否); `participant` 檔案 (`uploadFile` / `getFileInfo` / HTTP `getFile`) → 系統管理者或**任一頻道**之有效成員, `errChannelNotMember` (檔案不屬單一頻道、無 channelId 欄位, 不改 schema; 無任何頻道者無使用檔案之理由; 檔案 id 為伺服器產生之 UUIDv7, 可取得者限於能讀到引用它之訊息的頻道成員); `user` (`getWebInfor`、登入檢查) → 任一已驗證者. **清單與統計只回呼叫者有權看之頻道**: `getChannelsList` / HTTP `getChannels` (含 `agentId` 過濾) 與 `getStats` (`procCore.getStats(userId, scope)` 之 `scope` 為頻道 id 集合, 系統管理者不帶) 對一般使用者只含所屬頻道; 資料通道 `channels.select` / `channelMembers.select` (同步引擎供前端同步用, `authorizeExec` 只能整次放行或拒絕) 經 `operOrm` 包裝依呼叫者收斂為所屬頻道之列 (系統管理者全部; 非 select 或非陣列結果對一般使用者回空陣列). **成員判準單一處** `access.isMemberOf` / `memberChannelIds`: `channelMembers` 中 `(channelId, memberId=呼叫者 id, isActive='y')` 之列; 停用列、他頻道之列、非字串 `channelId` (含 `{ $ne: '' }` 之物件條件) 皆不算. 系統管理者對不存在之頻道交由業務函式處理 (`postMessage` / `ackChannel` / 成員存檔回 `errChannelNotFound`; 讀取類 `getMessages` / `getTasks` / `getArchived*` / `getChannelMembers` 回空陣列), 一般使用者一律 `errChannelNotMember`. 拒絕時記 `srLog.warn({ event:'access-denied', func, userId, err })` (不記 token 與請求內容), 並經 `wrapErrLog` / `runApi` 另記 err key.
  5. **不改既有契約**: 多人同時編輯寫入契約、刪頻道歸檔、狀態機守衛、lockSave 占位、`ackChannel` 兩段式皆不動——授權在入口邊界先於 procCore 套用, 被拒者零寫入; 授權通過後之行為與修前相同. 檢查與執行間之空窗 (毫秒級; 成員恰於其間被移除) 不處理, 同其他「讀後寫」之授權模型.

### D21. w-serv-orm 診斷輸出導入 srLog——只記 label 與不含個資之 safe, 不記 detail (2026-10-28)
- **狀態**: 採行 (主控派工第 154 項; w-serv-orm 1.1.20, Gitea issue #12).

## 已知限制 / 待討論 (合約外, 預設不做)

### L1. 頻道成員權限「弱enforcement」
- channelMembers 表記錄成員與角色, 但 v1 **不強制**「只有成員能在頻道發訊」(任何通過 token 認證者皆可發). 權限細化屬合約外.
- 若日後要強制, 在 postMessage 內加 membership 檢查即可 (單點).
- **2026-10-25 補記 (D20)**: 已強制——頻道內容 (含 `postMessage`) 限系統管理者或頻道成員, 單點為 `server/access.mjs`; 原載「不強制」不再成立, 保留為決策歷史.

### L2. 不實作本端 rate limit
- 速率限制屬 SSO 端或反向代理層責任, 本套件不重做 (對齊 w-web-api).

### L3. 單一頻道一個主責 agent
- channel.agentId 為單一主責 agent. 多 agent 共管屬合約外; 真要多 agent, 仍可各自輪詢同頻道 (claimTask 原子性保證不重複), getChannels 的 agentId 過濾以單一為準.

### L4. 任務無自動逾時/重派 (running→pending 僅人工)
- running 任務若 agent 中途死亡不會自動回 pending (自動恢復屬合約外, 未要求). 人類可手動 resetTask (running→pending) 救援停滯任務 — 此為 resetTask 的選用來源狀態 (error→pending 才是標準重試, 屬合約內). 後續若需要可加 timeClaim 逾時掃描.
- **確認 (2026-07-01)**: 任務卡在 running 為單一任務列之孤立問題, 不影響頻道其餘運作 — postMessage 建新訊息、開新任務 (新 pending 任務列) 皆與舊任務狀態無關; agent 只要仍存活並輪詢 getRecentMessages/getRecentTasks, 新訊息與新任務照常送達與可 claimTask. 僅該筆卡住的任務本身需人工 resetTask 才能重新被 claim (claimTask 守衛 state==='pending', running 中不可再搶). 維持現狀 (不加自動逾時掃描).

### L5. channelMembers 管理 UI (v2 已補: 各頻道內建成員管理入口)
- 後端 procCore 與 kpFunExt 提供 getChannelMembers / saveChannelMember / deleteChannelMember.
- **v2 決策 (2026-07-01)**: 各頻道聊天頁 (ChatView) 標題列加入「成員」入口, 開啟 WDialog 包覆既有 LayoutContentMembers (後台管理沿用之元件), 以新增 `fixedChannelId` prop 綁定當前頻道 — 給定時隱藏頻道選擇器, 直接管理該頻道成員, 免再選頻道. 後台管理「成員」子選單 (含頻道選擇器, 可切換管理任一頻道) 仍保留, 兩入口共用同一元件與 API, 僅差 `fixedChannelId` 是否綁定.
